## Что выполняет каждое задание

`normal`, `03:00` = 180 минут на одно задание, 4 CPU-слота/потока, `span[hosts=1]`, эксклюзивное выделение `-x`, точное ограничение `-m polus-c4-ib.bmc.hpc.cs.msu.ru`. На одном эксклюзивном узле задания выполняются последовательно. Время ожидания PEND не расходует RUNLIMIT; у кластера подтверждён `ABS_RUNLIMIT=Y`, то есть лимит абсолютный, без нормализации CPU.

Научная единица — датасет × модель × seed 101. Внутри задания: одна dense-модель, один общий split и checkpoint для семи методов × двух уровней 0.30/0.50, до 14 post-prune оценок. Полная кампания: 6 dense-моделей и 84 post-prune оценки. Архитектура L3/H32, до 500 эпох, patience 50, fine-tuning отключён; исходные научные параметры не менялись. Seeds 202/303 не запускаются.

`blimits -c -w -n limit_jobs` показывает `PER_USER=all`, `QUEUES=normal short`, `JOBS=4`. Это ограничение активных заданий пользователя, а не общего времени кампании. Несколько заданий могут ожидать в очереди; здесь эксклюзивный C4 сам ограничивает выполнение одним заданием одновременно.

## Изоляция и воспроизводимость

Для каждого условия отдельны:

- результаты и сводки runner: `results/pilot-cpu-101-c4-v2/jobs/CONDITION/`;
- научные артефакты: `…/seed_101/CONDITION/`;
- stdout научного процесса: `…/launcher-logs/CONDITION.log`;
- raw/processed-кэш: `data-by-condition/pilot-cpu-101-c4-v2/CONDITION/`;
- неизменяемые снимки launcher/адаптера, SHA256 и ответ `bsub`: `submissions/pilot-cpu-101-c4-v2/CONDITION/`.

Raw-файлы скопированы из ранее проверенного набора, все SHA256 сверены. Так два задания для одного датасета не записывают общий `data.pt`. Репозиторий исследования закреплён на `72293149d8fff186dd268789e7b8fea5848c9360` и остаётся чистым.

Общие сводки собирает отдельно и последовательно `collect-pilot-status.py`, без загрузки GNN. Он принимает только завершённые условия с проверенным набором 14 method/target-строк и не включает test-метрики в таблицу сравнения. Пока все шесть условий не закончились, статус кампании — неполный.

## Скрипт постановки

Просмотр всех шести заданий без изменений:

```bash
bash submit-pilot.sh --all --dry-run
```

`--prepare` только формирует конфигурации и проверенные raw-копии, без `bsub`. Обычный вызов отправляет выбранное условие, `--all` — шесть условий. Скрипт проверяет весь выбранный набор до первой отправки, сохраняет INTENT/ACCEPTED и ID каждого задания, не повторяет отправки автоматически и отказывается повторно использовать уже зарегистрированное условие.

**Текущие шесть заданий уже отправлены.** Для будущей отдельно авторизованной кампании имя можно задать через `POLUS_CAMPAIGN`; seed и научная матрица при этом остаются прежними. Незавершённые/неудачные опыты не перезаписываются.

## Первая попытка и исправление launcher

Задания 1598688–1598693 относятся к предыдущей инфраструктурной попытке, не к итоговой v2. Первый научный процесс завершился успешно, но проверка runner ожидала CSV в другом каталоге: runner создавал каталог для `launcher.log`, а научный pipeline при `resume=False` автоматически выбирал имя с `_001`. Остальные задания этой попытки остановлены, данные сохранены в `results/pilot-cpu-101/jobs/`.

Внешний адаптер теперь размещает launcher-log вне каталога условия, чтобы его создавал сам pipeline. Менялась только файловая оркестрация; обучение, прунинг и исходные validators не переписывались. Специальная регрессионная проверка с полностью подменённым научным subprocess прошла: `logs/launcher-directory-regression.txt`. Параметры всех шести YAML сравнены с исходными и совпали, кроме путей: `logs/six-c4-v2-preflight.json`.

Рецепт директив LSF основан на [normal-примере курса](https://github.com/r1zons/cmc_msu_hpc_course_2026/blob/main/scripts/polus/large_grid_pilot_n256.lsf). В него добавлены ограничение C4 и изоляция GNN-условий.
