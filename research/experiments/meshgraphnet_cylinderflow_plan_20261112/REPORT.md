# MeshGraphNet на CylinderFlow · план пилота POLUS

**Последующий этап** описан в [техническом отчёте POLUS](TECHNICAL_REPORT.md). Он содержит результаты P100 и измеренный прогноз для пилота обучения.

12 ноября 2026 · протокол на рассмотрении. Проверены исходники, публичные метаданные и сохранённые журналы. Целевой вариант — двухкомпонентная модель DeepMind. Для технической проверки достаточно одного графа и инициализированной модели. Для научного сравнения нужен пригодный замороженный checkpoint с документированным обучением. Модель и данные траекторий на POLUS в рамках этого этапа не загружались.

Гипотеза пилота — выбор каналов по короткому rollout уменьшает ошибку на 100-м шаге по сравнению с одношаговым выбором при том же физическом сжатии. Постановка — минимизировать $E_H(m)$ при $P(m) \le (1-r)P_0$, где $m$ задаёт оставленные каналы. Пилот сравнивает три способа приближения к этому минимуму на ограниченной библиотеке масок.

1. **Данные и конфигурация.** Отдельная конфигурация и модуль для траекторий. Сохранить официальные train/valid/test. Назначить ID `split:record_ordinal` в исходном порядке, закрепить generation и SHA256 источника и каждой преобразованной записи. Зависимость от конвертера не переносить в GPU-окружение. Проверить CRC32C записей, конечность, dtype, индексы, граничные типы, кадры и уникальность рёбер. Проверку дубликатов между splits проводить по хешам содержимого, проверяющему процессу отдавать только хеши test до финальной оценки. Для первого запуска достаточно одной validation-записи. Обновлять только `NORMAL` и `OUTFLOW`, остальные скорости копировать из текущего состояния. После исходного кадра ни одна эталонная скорость не подаётся на вход. ## Минимальный научный пилот

**Выбор входов.** Один замороженный двухкомпонентный dense-checkpoint. После инвентаризации взять официальные ID по порядку и перемешать отдельно для valid/test через `random.Random(101)` и `random.Random(202)` под Python 3.10. Из valid выделить 16 траекторий для выбора dense-checkpoint и контроля качества, следующие 8 для диагностики, ещё 8 для отбора каналов. Из test закрепить первые 20 ID по манифесту, открыть их только после фиксации всех масок, правил и первичной метрики. Для диагностики и финальной оценки начальные кадры 100 и 300 (нулевая индексация raw). Для выбора каналов один старт в кадре 200. Фиксировать все ID и окна до оценивания. Для dense-validation использовать те же два стартовых кадра, что для диагностики.

**Метрики.** Для каждой траектории и окна $e_h$ — MSE по двум компонентам скорости на активных узлах в кадре $t_0+h$, в физических единицах. Основная метрика — $E_{100}$, среднее $e_{100}$ сначала по окнам одной траектории, затем с равным весом по траекториям. Показать также $E_1,E_5,E_{20},E_{50}$ и отдельно среднее ошибок от шага 1 до $H$ для 20 и 100. Для сопоставления с кодом DeepMind добавить MSE по всем узлам и шагам до $H$. Nonfinite или сорванные rollout сохранять отдельными отказами, с числом и моментом отказа. Стабильность оценивается до количественного сравнения. [Семантика метрик DeepMind](https://github.com/google-deepmind/deepmind-research/blob/34b2486902f082ad3a58bffebdc499c84c93d31c/meshgraphnets/cfd_eval.py)

**Диагностика чувствительности.** Сделать 24 маски от dense без использования оценок на данных. В каждой удалить по 4 канала из каждого допустимого MLP, всего 120 каналов или 30 840 параметров. По восемь масок с равномерным выбором каналов внутри нижней, средней и верхней трети dense-ранга в каждом MLP, без повторов целых масок, seed 101. Значимость канала — произведение L2-нормы его входящей строки с bias и L2-нормы исходящего столбца. Оценить парные $\Delta e_1,\Delta e_{20},\Delta e_{100}$ относительно dense. Сообщить Spearman по средним эффектам масок, инверсии порядка и расхождения знака $\Delta$ с учётом численной погрешности. Интервалы строить повторной выборкой целых траекторий, сохраняя все маски и оба окна вместе. Результат условен на одном checkpoint и заранее заданном наборе масок. Наблюдения на узлах, кадрах и масках одной траектории не дают независимых повторов.

**Сравнение трёх стратегий.** Одна цель $r=10\%$ физического уменьшения. Удалить ровно $K=\lceil rP_0/257\rceil$ каналов с одинаковым конечным вектором ширин. Для ожидаемого $P_0$ это 908 каналов и 233 356 параметров. Раздать удаляемые каналы поровну между MLP, остаток назначить в заранее закреплённом порядке «блок, тип MLP». Провести четыре шага с покомпонентными порциями не более 8 каналов на MLP, 8, 8, 8 и остаток 6 или 7 для ожидаемого счёта. Общий генератор даёт до 8 уникальных кандидатных масок на шаге. Одна удаляет самые низкоранговые доступные каналы в каждом MLP, ещё до семи выбираются с seed 101 из нижних $2k$ доступных каналов при порции $k$. Ранги фиксируются на dense. Генератор одинаков условно на текущей маске. При одинаковой истории список совпадает; после расхождения применяются те же правила к оставшимся каналам.

| Выбор | Критерий в одной и той же библиотеке кандидатов |
|---|---|
| Weight magnitude | Минимальная сумма dense-рангов удаляемых каналов, без validation-forward |
| One-step | Минимум $E_1$ на восьми selection-траекториях |
| Short rollout | Минимум среднего $E_1,\ldots,E_5$ на тех же траекториях, с обратной связью |

На каждом шаге применить одну маску к текущей модели, затем заново построить кандидатов. Использовать одинаковый лексикографический порядок исходных ID для совпадающих оценок. Кандидат с нечисловой validation-ошибкой отклонить с записью причины. Если допустимых кандидатов не осталось, остановить метод и зафиксировать недостижение бюджета. До раскрытия test сохранить конечные маски, полный счёт параметров и остановки. Fine-tuning отсутствует. Показать различия масок и парные эффекты относительно dense и magnitude. Для каждого метода отдельно сохранить wall time поиска, число кандидатов, запросов и реальных forward, время физического удаления, inference latency и peak memory. Сравнение относится к заданной библиотеке кандидатов и её стоимости.

**Критерий решения.** До открытия test зафиксировать практический порог $\delta=0.01\,E_{100}^{dense,valid}$ на отдельном dense-validation поднаборе. Основной эффект — среднее парное $E_{100}^{short}-E_{100}^{one}$. Сравнивать 95%-й парный bootstrap-интервал по 20 целым test-траекториям (10 000 реплик, seed 101). Интервал целиком ниже $-\delta$ при сопоставимой стабильности поддерживает гипотезу для этого checkpoint. Интервал целиком выше $+\delta$ или целиком внутри $[-\delta,+\delta]$ ослабляет соответственно гипотезу о направлении или о практически значимом эффекте. Остальное, в том числе неоднозначная стабильность, считать неопределённым. Диагностические инверсии мотивируют проверку механизма, но не устанавливают причинность. Повторение потребует независимых dense seeds и отдельного подтверждающего плана. Научный вклад проверяется сравнением критериев выбора и анализом их расхождений, а новизна требует отдельного обзора литературы.

## Ресурсы и решение о расширении

- **Хранилище.** Исходники данных занимают около 16,37 GB десятичных. Для оригиналов и потоковой конверсии с запасом предварительно выделить 35–45 GB. Для первого технического запуска достаточно одного преобразованного validation-графа, при необходимости ещё одного train-графа. Доступ POLUS к GCS и локальные квоты не измерялись.
- **Инференс и поиск.** При $N\approx1900$, $E\approx11000$ направленных рёбер и FP32 одна конкатенация edge MLP занимает около 16 MiB. Плановый диапазон — 0,3–2 ГиБ GPU при последовательном инференсе без сохранения активаций и 2–8 ГиБ для обучения на двух графах. Это грубые оценки до измерений, включая неопределённость максимального размера графа. Диагностика требует до 40 000 forward, сравнение критериев — до 1536, финальная оценка dense и трёх масок — до 16 000. Проверка одного dense-checkpoint на 16 validation-траекториях требует ещё 3200 forward. При допущении 10–100 мс на forward это около 10–102 минут чистого суммарного GPU-времени, до накладных расходов, повторных замеров и очереди. Поиск поместить в одно задание после измерений, независимую диагностику и финальную оценку при необходимости делить по целым траекториям.
- **Dense-обучение при отсутствии весов.** FP32, Adam, batch 2, validation-отбор по $E_{100}$, тренировочные нормализаторы и шум 0,02 на `NORMAL` как в референсе. Закрепить формулу шумовой коррекции и расписание LR по исходному коду. Официальный demo runner предусматривает первые 1000 шагов на накопление статистик и общий предел 10 млн шагов. Сначала измерить 200 устойчивых optimizer steps после накопления статистик, затем отдельно согласовать бюджет. При условных 0,1–1,0 с на optimizer step 10 000 шагов займут 0,28–2,78 GPU-часа, а 10 млн — 278–2778 GPU-часов до I/O и validation. Короткий бюджет служит для проверки пригодности, достижение качества за это время неизвестно. При продолжении между заданиями сохранять optimizer, нормализаторы, RNG, шаг и sampler state. [Настройки референса](https://github.com/google-deepmind/deepmind-research/blob/34b2486902f082ad3a58bffebdc499c84c93d31c/meshgraphnets/run_model.py)

**GO после согласования для одного технического задания. NO-GO для научного сравнения до технического PASS и замороженного dense-checkpoint**, который на всех 16 dense-validation траекториях даёт конечный rollout и по среднему $E_{100}$ минимум на 10% превосходит persistence с теми же границами. Дополнительно нужны подтверждённые split- и checkpoint-хеши, измеренный прогноз на каждое задание с запасом не менее 25% до лимита очереди, точное совпадение параметров между тремя стратегиями и численно устойчивый отбор. При отсутствии подходящих весов или при провале плотной модели потребуется отдельное решение о бюджете обучения. Расширение после пилота зависит от парных эффектов, неопределённости, стабильности и стоимости поиска. Уменьшение числа параметров и измеренное ускорение оцениваются отдельно.

## Решения до научного сравнения

- **Набор масок открыт.** Вариант с отбором из нижних $2k$ ограничивает вывод областью малой magnitude. В следующей версии предусмотреть общую библиотеку для трёх методов с magnitude-кандидатом, выборкой из полного допустимого ранга и масками из средних и верхних рангов. Доли, размер библиотеки и генератор зафиксировать до финальной оценки. Число удалённых каналов и конечные ширины по-прежнему должны совпадать.
- **Горизонты открыты.** Пять шагов для выбора и 100 для оценки — параметры пилота. Обосновать их по длительности характерных изменений скорости, диагностике на validation и измеренной цене поиска. Длинная оценка должна выходить за горизонт отбора. Выбранный горизонт и первичную метрику закрепить до доступа к test.
- **Пороги открыты.** Значения 1% dense-ошибки для практически важного эффекта и 10% улучшения над persistence предложены как рабочие ориентиры. Перед финальной оценкой сопоставить их с физическими единицами, разбросом ошибок на validation, численной погрешностью и требуемым качеством. Эти решения не используют test.
